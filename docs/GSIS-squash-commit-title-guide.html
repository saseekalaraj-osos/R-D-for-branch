GSIS Squash Commit Title Standard

How feature and bug pull requests get automatic commit titles on base-v2

For the development team  |  Workflow: .github/workflows/feature-commit-title.yml

Goal. Every squash merge into base-v2 should have one clean commit title: Jira id + global F sequence. Bug PRs also mark BUG and, when present, the related feature/story Jira and a clickable link to that feature PR.

1. How it works

  1. Developer opens a PR into base-v2 from a named feature or bug branch.
  2. GitHub Action reads the branch name, finds the next global F number on base-v2, and sets the PR title.
  3. Reviewer squash-merges. GitHub uses the PR title as the squash commit message.
  4. GitHub always appends the current PR number as (#16). That is clickable on the commits page.

The workflow does not rewrite git history. It only updates the PR title.

2. Required GitHub repository settings

Repo → Settings → General → Pull Requests

SettingValueWhy
Allow squash mergingOnOne commit per PR on base-v2
Default squash commit messagePull request titleUses the auto-generated title
Allow merge commitsOffOtherwise feature commits appear on base-v2
Allow rebase mergingOff (recommended)Keeps history linear and titles consistent
Always click Squash and merge. Do not use “Create a merge commit”. A merge commit keeps every feature-branch commit on base-v2.

3. Branch naming

TypeBranch patternExample
Feature / story feature/GSIS-<storyId>-<short-name> feature/GSIS-3654-leave-api
Bug (general) bug/fix/GSIS-<bugId>-<short-name> bug/fix/GSIS-2875-null-list
Bug linked to a story bug/fix/GSIS-<bugId>-GSIS-<storyId> bug/fix/GSIS-2875-GSIS-3654

The story id on a bug branch is optional. Use it only when the bug belongs to an existing feature/story (same id as feature/GSIS-3654-...).

4. Global F sequence

F is a running number for the whole base-v2 branch. It is not per Jira id.

Merge orderPRCommit title (before GitHub adds PR number)
1st merged PRFeature GSIS-12345GSIS-12345-F1
2nd merged PRFeature GSIS-54852GSIS-54852-F2
12th merged PRBug GSIS-2875 for story GSIS-3654GSIS-2875-BUG-F12-GSIS-3654

Open PRs are numbered in the order they were created. After a merge, remaining open PRs are retitled to the next F numbers.

5. Scenarios

S1 Feature pull request

Branch: feature/GSIS-3654-leave-api

PR title set by workflow: GSIS-3654-F6

After squash merge (GitHub adds PR number): GSIS-3654-F6 (#11)

(#11) is a clickable link to that feature PR on the commits page.

S2 Next feature uses the next F number (different Jira)

Branch: feature/GSIS-3214-employee-api

PR title: GSIS-3214-F7

After squash: GSIS-3214-F7 (#10)

F continues globally even though the Jira id changed.

S3 General bug (no story / feature id)

Branch: bug/fix/GSIS-2875 or bug/fix/GSIS-2875-null-list

PR title: GSIS-2875-BUG-F12

After squash: GSIS-2875-BUG-F12 (#16)

Use this for standalone bugs that are not tied to a feature branch.

S4 Bug linked to a feature/story Jira

Branch: bug/fix/GSIS-2875-GSIS-3654

First id = bug ticket. Second id = story/feature ticket (same as feature/GSIS-3654-...).

PR title: GSIS-2875-BUG-F12-GSIS-3654

After squash: GSIS-2875-BUG-F12-GSIS-3654 (#16)

The story id is optional. If it is on the branch, it is included so the bug commit lines up with the feature git branch.

S5 Bug + story, and link the feature PR (same as #16)

When the bug branch contains a story id, the workflow finds the matching feature branch/PR (feature/GSIS-3654-... or the squash commit already on base-v2) and puts that PR number in the title. GitHub still appends the bug PR number.

PR title set by workflow: GSIS-2875-BUG-F12-GSIS-3654 (#6)

After squash: GSIS-2875-BUG-F12-GSIS-3654 (#6) (#16)

PartMeaningClickable?
GSIS-2875Bug JiraNo (text)
BUGThis PR is a bugfix—
F1212th squash on base-v2—
GSIS-3654Related feature/story Jira and git branchNo (text)
(#6)Feature PR for feature/GSIS-3654-...Yes, like #16
(#16)This bug PR (added by GitHub)Yes

If no feature PR/branch is found, the extra (#6) is omitted. The story id in the title is still kept.

S6 Several open PRs at once

PRs are titled in created-at order.

Open PR (created order)Assigned title
Feature GSIS-4145GSIS-4145-F9
Feature GSIS-2541GSIS-2541-F10
Bug GSIS-1254GSIS-1254-BUG-F11

When F9 is merged, the workflow runs again and remaining open PRs move to F10, F11, …

S7 Draft PRs

Draft PRs are skipped. When the PR is marked ready for review, it gets the next F title.

6. What you must not do

ActionResult
Create a merge commit instead of squash Feature-branch commits appear on base-v2 (example: “GSIS-7894 customer API implement” plus “Merge pull request #2”). Title standard is lost.
Amend / force-push base-v2 to strip (#16) A shallow checkout can turn base-v2 into a single root commit. GitHub then shows only one commit and cannot open new PRs (“No common ancestor”).
Wrong branch name (no GSIS- id) Workflow skips the PR. Title is not generated.
Edit the squash title by hand and drop the Jira/F part The next F number may be wrong because the workflow counts titles matching the pattern.

7. Developer checklist

  1. Create the branch with the correct prefix and Jira id(s).
  2. Open a PR into base-v2 (not draft, or mark ready when it is).
  3. Wait for the Action to set the PR title. Do not rename it unless the Action failed.
  4. Review and squash-merge. Leave the commit title as the PR title.
  5. GitHub will add (#PR). That is expected. Do not try to remove it with a history rewrite.
Quick examples to show the team
Feature: feature/GSIS-3654-leave-api → GSIS-3654-F6 (#11)
General bug: bug/fix/GSIS-1254-data-empty → GSIS-1254-BUG-F11 (#9)
Bug + story: bug/fix/GSIS-2875-GSIS-3654 → GSIS-2875-BUG-F12-GSIS-3654 (#6) (#16)

8. FAQ

Why does the commit show (#16)?
GitHub always appends the squash PR number. There is no repository setting to turn that off. It is useful because it links the commit to the PR.

Can we hide (#16)?
You can delete it in the squash dialog before confirming, but the team standard is to keep it. Do not force-push base-v2 to strip it.

Why BUG in the title?
So bugfixes are visible in history next to feature F commits, and so the id is the bug Jira, not the story Jira.

What if the bug is not related to any feature?
Omit the second Jira from the branch. Title stays GSIS-2875-BUG-F12.

What if the feature PR is not found?
The story id is still in the title. Only the extra clickable (#featurePR) is missing.

Does this apply only to base-v2?
Yes. The workflow runs on PRs and pushes targeting base-v2.
